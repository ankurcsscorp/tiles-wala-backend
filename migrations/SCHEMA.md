# Billing database schema

Migration 034 adds `stores.invoice_payment_details` (JSONB object, default `{}`) and `sales_invoices.payment_details_snapshot` (nullable JSONB object). Existing store terms fields are reused. Finalization captures payment details; finalized payment/terms snapshots are immutable. No historical invoice rows or live store account values are backfilled. See [invoice footer settings](../docs/INVOICE_SETTINGS.md#sales-invoice-terms-and-payment-instructions).

Migration 027 corrects invoice allocation capacity to exclude reversed payments while retaining their history. It adds no columns and rewrites no financial records. Apply before using automatic oldest-first customer receipt allocation. See [payment behavior and verification](../docs/PAYMENTS.md). The down migration restores the earlier guard and may prevent replacement allocation after reversals; prefer a forward correction after use.

Migration 026 makes Non-GST Simple Billing the default, with explicit GST opt-in. It changes config defaults and audits conversion of incomplete/legacy preferences, preserving completed detailed GST configs and all invoice history/registration identifiers. It revises sales/purchase Non-GST registration gates while retaining zero-tax, math, immutability, inventory, and accounting guards. Apply with `npm run migrate`; see [current billing behavior](../docs/INVOICE_SETTINGS.md). Rollback refuses incompatible historical records and does not restore preferences; prefer a reviewed forward correction.

Migration 025 adds account activation and permission overrides to `users`, plus `role_permission_settings` for non-admin type defaults. Existing store assignments remain authoritative for store scope. Access changes use the existing audit ledger. See [Manage Users](../docs/USER_MANAGEMENT.md) for the permission hierarchy, APIs, and rollout requirements.

Migration `001_multi_store_foundation.sql` adds a shared product master and store-scoped billing/inventory model. `users` is reused as the identity table; it is not duplicated. Existing collections, enquiry, and bonus tables are not changed.

Migrations `004` and `005` extend store profiles with city/state/PIN, optional GSTIN and logo, invoice numbering preferences and footer/terms, then snapshot store name, address, tax ID, phone, and email automatically when a sales or purchase invoice is posted.

Migration `006_product_and_unit_management.sql` extends the existing shared `products` and `units_of_measure` tables, adds `product_categories`, and adds per-product `product_unit_conversions`. It seeds only generic unit definitions (Box, Piece, Square foot, Square meter); it does not create product records or assign prices, HSN codes, or tax rates. `default_purchase_price` is per configured purchase unit and `default_selling_price` is per configured sales unit. `factor_to_base` means how many base units one configured unit represents. Migration 007 enforces case-insensitive SKU uniqueness; it stops with an actionable error if existing SKUs collide rather than deleting or rewriting product data.

Migration `008_customer_management.sql` extends the original shared `customers` table (it does not create a second customer master). Existing `phone`, `address`, and `tax_id` remain the primary mobile, billing address, and optional GSTIN fields; alternate mobile, shipping address, city/state/PIN, customer type, credit limit, payment terms, and notes are added. Contact numbers are indexed but deliberately not unique. Opening balances and later corrections are posted to `customer_balance_adjustments`, attributed to a store and direction. Customer outstanding values are derived from posted sales invoices, posted inbound payment allocations, posted sales returns, and posted balance adjustments; no editable balance column is stored.

Migration `009_customer_payment_link.sql` adds an optional customer reference to inbound payments for unapplied receipts and advances. Historical payments are linked only when all allocated sales invoices belong to one customer. A deferred constraint trigger prevents a linked payment from being allocated to another customer's invoice. Customer credits include the unallocated remainder of posted receipts; payments without a customer link and without an allocation cannot be attributed to a customer.

Migration `010_supplier_management.sql` extends the existing shared `suppliers` table with contact person, location, payment terms, and notes; it does not recreate the supplier master. `supplier_balance_adjustments` stores store-attributed opening balances and corrections. Outbound `payments.supplier_id` identifies unapplied supplier payments; historical payments are linked only when all allocated purchase invoices belong to one supplier. Deferred checks prevent linked supplier payments from being allocated to another supplier's invoice. Payable balances derive from posted purchases less posted payment allocations, unallocated supplier payments, and posted purchase returns, plus/minus posted adjustments.

## Relationships

- `user_store_assignments` joins existing `users` to `stores`, with one assignment per pair and at most one active default store per user.
- `products.base_unit_id` points to `units_of_measure`. Inventory balances are keyed by `(store_id, product_id)`; stock movements link a store/product to a source document and update the balance atomically.
- `store_billing_config` holds per-store tax and numbering preferences. `invoice_number_sequences` serializes allocation by store, document type, series, and period; document tables also enforce unique `(store_id, series, invoice_number)` values.
- `purchase_invoices` belong to a store and supplier; `purchase_invoice_items` belong to a purchase invoice and product/unit. Sales invoices similarly reference an optional customer and have immutable descriptive and price snapshots in their lines.
- Purchase invoice items snapshot SKU, name, product attributes, HSN, unit label and conversion factor, purchase rate, discount, taxable value, tax rate/amount, and line total. Purchase header freight, additional charges, and round-off are included in the server-validated grand total.
- `purchase_receipts` belong to a posted purchase invoice and store. `purchase_receipt_items` reference invoice lines and record received quantities. Repeated partial receipts are serialized on the invoice row and cumulative posted quantities cannot exceed the invoice quantities. Posting creates ledger entries; reversing a receipt creates compensating movements.
- `sales_invoices` belong to a store and optionally a shared customer. Drafts have no invoice number; finalization allocates a unique store/series/period number under the `invoice_number_sequences` row lock. Sales invoice items snapshot product, unit, conversion, price, discount, and tax details. Posted invoice headers snapshot store branding, terms, customer details, salesperson name, and tax jurisdiction.
- `payments` belong to one store and have an `in` or `out` direction. `payment_allocations` connect an inbound payment to posted sales invoices or an outbound payment to posted purchase invoices. Composite foreign keys enforce matching store and direction; trigger checks serialize allocation and cap aggregate allocations at both payment and invoice totals.
- `payment_method_options` stores active system and custom method codes. Payments reference one configured code. `customer_request_key` and `purchase_request_key` prevent duplicate receipts/payments after a client retry. `reversal_reason`, `reversed_by`, and `reversed_at` describe reversals; allocations remain attached to the original payment for audit history and cease affecting balances when payment status becomes `reversed`.
- `stock_transfers` identify source and destination stores, with transfer lines in `stock_transfer_items`. Migration 015 adds dispatch/receipt actors and timestamps, dispatched quantities, immutable `stock_transfer_receipts` and receipt lines, and the append-only `stock_transfer_transit_movements` ledger for the virtual `IN_TRANSIT` location. Sales and purchase returns reference their originating invoice and lines.
- `stock_adjustments` records a store, required reason, actor, and idempotency key; `stock_adjustment_items` records product, unit, decimal quantity, and increase/decrease direction. Invoice, return, transfer, and adjustment posting triggers add movements to `stock_movements`; reversal creates compensating movements tied to their original movement rows.
- `audit_logs` optionally reference a store and actor while retaining JSON before/after snapshots.
- Sales billing APIs are mounted at `/api/tiles/sales` and require Admin or Salesperson authentication plus assigned store access. Draft save and finalization calculations use PostgreSQL `NUMERIC`; client totals are ignored. Finalization saves the invoice number, tax breakdown, optional receipt/payment allocation, audit event, and stock movements atomically. A failed stock movement or allocation rolls the transaction back. Outstanding balance is derived from posted payment allocations rather than stored on the invoice.
- Payment APIs are mounted at `/api/tiles/payments`. Customer receipts and supplier payments can allocate across multiple same-store invoices for the selected party; unallocated advances are supported. Payment rows and allocations are immutable after posting. A reversal records its actor, reason, timestamp, and audit event while preserving allocations; only posted payments count toward invoice balances. Daily reports show posted inflow/outflow and reversed amounts by date and method.
- Store administration APIs are mounted at `/api/tiles/stores`; assignments authorize non-admin access to active stores, while the existing Admin role remains global.
- Products are shared in `products`; store quantities remain in `inventory_balances` and are changed only through stock movements. Product APIs expose store stock only to an authorized assignee and business-wide stock only to Admin. Product price lookup converts configured purchase/sales prices using product-specific factors and PostgreSQL NUMERIC arithmetic.

Amounts use `NUMERIC(18,2)` or `NUMERIC(18,4)` and quantities use `NUMERIC(18,4)`. Invoice balances are intentionally not stored: derive them from posted totals, allocations, and returns. Stock balance is a maintained projection of the stock movement ledger; movement insertion and balance update share one database transaction. Migration 002 prevents direct balance edits and makes the movement ledger immutable. Idempotency keys and source uniqueness prevent posting a movement twice. Migration 003 requires documents to start as drafts, permits only draft→posted/cancelled and posted→reversed transitions, freezes posted document headers and lines, and makes cancelled/reversed documents terminal. Billing services must reverse a posted document and create its compensating movements in one database transaction.

Migration 013 adds sales invoice discounts, taxable/tax jurisdiction summaries, CGST/SGST/IGST allocation, additional charges, round-off, and finalized print snapshots. Store sequence allocation is serialized per store, sales series, and invoice period. Draft invoices do not reserve or deduct stock. Finalized invoices create immutable stock movements via the existing ledger trigger; posted invoices with payments or posted returns cannot be reversed until those linked accounting documents are reversed.

## Existing tables reused

- `users`: user identity and foreign-key target for staff assignments, document creators, and audit actors.
- `customers`: existing shared customer identity and contact record, referenced by sales invoices from multiple stores.
- `suppliers`: existing shared supplier identity and contact record, referenced by purchase invoices from multiple stores.

`sales_bonus_product_config` remains separate because it stores bonus defaults keyed by product name and is not a canonical inventory catalog. The billing foundation's existing shared product, unit, customer, and supplier tables are reused by their respective management modules.

## Customer balances and access

`sales_invoices.customer_id` links one shared customer to store-specific invoices. A payment may be allocated across invoices through `payment_allocations`; ledger reporting sums each allocation against the invoice's customer and store. Posted sales returns reduce the originating customer's balance. `customer_balance_adjustments` supports store-attributed opening balances and corrective entries; its partial unique index permits only one unreversed opening balance per customer. Admin sees financial history across all stores; Salesperson reads are restricted to assigned active stores. Customer profile and financial routes require Admin or Salesperson authentication.

`purchase_invoices.supplier_id` links one shared supplier to store-specific purchases. Outbound payment allocations are joined through `payment_allocations`; posted purchase returns lower the amount payable. `supplier_balance_adjustments` stores store-attributed opening payables and corrections. Admin sees history across all stores; Salesperson reads are restricted to assigned active stores. Supplier profile and financial routes require Admin or Salesperson authentication.

Inventory quantities are held in the shared base unit and summarized by `(store_id, product_id)` in `inventory_balances`; `stock_movements` is the source ledger, and its existing insert trigger updates balances atomically while preventing negative quantities. Migration 011 adds reasoned stock adjustment documents and posting hooks for purchases, sales, returns, and adjustments. Migration 015 handles store transfers through explicit dispatch and receipt transactions; source stock moves into `IN_TRANSIT` on dispatch and only accepted units enter destination stock on receipt. The dispatch-time unit conversion is snapshotted, and received, damaged, and shortage quantities must reconcile to dispatched quantities. Transit inventory contributes to authorized business-wide inventory totals and has a separate reconciliation check. Document reversals write compensating movements. Stock valuations use the product's configured purchase price translated through its product-specific conversion factor; absent purchase prices remain unvalued. Reservation is not yet implemented, so API responses use zero reserved quantity.

Transfer APIs are mounted at `/api/tiles/transfers`. Creating or editing a draft requires inventory manager access (`owner`, `manager`, or `inventory`) to both stores. Dispatch requires source-store access; receipt requires destination-store access. Drafts can be cancelled; dispatched transfers must be received and reconciled, while received transfers are immutable and corrections use authorized stock adjustments.

Migration 016 reuses `sales_returns`, `sales_return_items`, `purchase_returns`, and `purchase_return_items`. Sales return lines snapshot invoice pricing and tax, reason, product condition, and quantities assigned to restock, quarantine, or supplier-return-pending disposition. Only restock quantity is added to sellable inventory. Sales return drafts require manager approval before posting; posted returns credit customer accounts, with explicit refund and remaining customer-credit values. Purchase returns are limited to quantities received from their original purchase invoice and credit the supplier ledger. Both workflows retain invoice and item references, use store sequence numbers, preserve immutable source invoices, and post document, stock, and audit changes transactionally. See migration 016 and its execution/rollback notes in `migrations/README.md`.

Financial ledgers and reports are served at `/api/tiles/financial-reports`. Ledger rows derive from posted invoices, posted payment allocations, unallocated posted payments, posted returns and posted balance adjustments; reversed payments are excluded while their original rows and reversal details remain available through payment history. Ledgers return opening/closing balances, store-specific running balances, date-range filtering, offset pagination, source transaction IDs, and CSV export. Outstanding summaries separate receivables and payables by authorized store and across the business. Invoice aging is as of a selected date and uses the invoice due date, falling back to invoice date plus configured customer/supplier payment terms. Unallocated advances affect outstanding balances but do not get silently assigned to invoice aging buckets; invoice aging uses allocations and posted return credits only.

The business dashboard is served at `/api/tiles/dashboard`; it aggregates posted sales, purchases, payments, inventory, and financial outstanding values in PostgreSQL. Every summary and report query is restricted to the user's active store assignments, or all active stores for Admin. Dashboard report types include sales and purchases by date/store/product/customer/supplier/salesperson, stock by store, low stock, stock movements, transfers, returns, and payment methods. Results support date filters and offset pagination. Inventory valuation is an indicative projection using the configured default purchase price and product conversion; the application does not capture a reliable cost-of-goods snapshot on sales lines, so gross profit is intentionally reported as unavailable. Migration 017 adds store/date indexes for stock movement and return reporting. Apply it with `npm run migrate`; rollback with `npm run migrate:down -- 017_reporting_indexes.sql` (the rollback only removes indexes).

Posted sales invoice, purchase invoice, and payment reversals require Admin or an active `owner`/`manager` assignment at the document's store. Goods receipt reversals require Admin or `owner`/`manager`/`inventory`. Purchase return posting requires Admin or `owner`/`manager`; sales return posting requires manager approval. Draft sales invoice cancellation uses a separate route from posted invoice reversal.

## Invoice-style return workflows (028–032)

The existing return headers/items now distinguish historical workflow version 1 from new version 2. Version 2 stores settlement mode, original document/product/tax/conversion snapshots, finalization request keys, original component reversals, and initial settlement snapshots. Current effective credits derive from actual posted return-linked refund payments, not editable balances. `payments.sales_return_id` / `purchase_return_id` identify customer cash-out and supplier cash-in refunds; ordinary payment allocation rejects these refund rows.

`return_credit_allocations` is an immutable store/party-validated link from a return to a due sales/purchase invoice. Legacy returns preserve implicit originating-invoice credits through `sales_invoice_return_credits` / `purchase_invoice_return_credits`; new returns contribute only explicit allocations to invoice due balances. `sales_return_accounting` / `purchase_return_accounting` supply effective party credit/refund projections. Unapplied return credit can later be allocated oldest first without changing party net balance.

`return_inventory_movements` tracks append-only DAMAGED/PENDING_INSPECTION base-unit stock separately from available `inventory_balances`. Sellable return receipt and purchase return dispatch reuse `stock_movements`. Pending inspection appends bucket debit and sellable/damaged acceptance. Posting checks remaining original quantities and received purchase quantities while holding invoice and product/bucket locks. Reversal compensates original and inspection movements; negative stock and unreversed actual refunds block it. Invoice/receipt dependency triggers prevent related reversals from invalidating active returns. Posted metadata/line/totals guards, payment capacity, manager roles, module permissions and audit evidence apply transactionally. See [return workflow guide](../docs/RETURNS.md) for API, calculation, historical and print scope.

Migration 033 extends sales return source validation to every original invoice referenced by `sales_return_items.sales_invoice_item_id`. All sources must be posted for the same customer/store; the header `sales_invoice_id` remains an anchor for existing party accounting. Per-line invoice snapshots and `document_snapshot.invoices` preserve all actual source references for new records. Posting locks every original, and active combined returns block reversal of secondary sources. No new balance tables or changes to historical amounts are introduced. Purchases retain their single-invoice source policy.

Party ledger statements reuse existing invoice, payment, return and balance-adjustment entries without schema changes. The shared report service reads totals and rows in a repeatable-read, read-only snapshot and supplies one combined running balance plus per-store balances. Full print/PDF/CSV exports include explicit opening and closing rows and movement totals. See [ledger statements](../docs/LEDGER_STATEMENTS.md).
