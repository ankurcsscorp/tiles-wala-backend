# Database migrations

Migration 027 corrects invoice allocation capacity to exclude reversed payments while retaining their history. It adds no columns and rewrites no financial records. Apply before using automatic oldest-first customer receipt allocation. See [payment behavior and verification](../docs/PAYMENTS.md). The down migration restores the earlier guard and may prevent replacement allocation after reversals; prefer a forward correction after use.

Migration 026 makes Non-GST Simple Billing the default, with explicit GST opt-in. It changes config defaults and audits conversion of incomplete/legacy preferences, preserving completed detailed GST configs and all invoice history/registration identifiers. It revises sales/purchase Non-GST registration gates while retaining zero-tax, math, immutability, inventory, and accounting guards. Apply with `npm run migrate`; see [current billing behavior](../docs/INVOICE_SETTINGS.md). Rollback refuses incompatible historical records and does not restore preferences; prefer a reviewed forward correction.

Migration 025 adds active-account status, per-user permissions, and user-type permission defaults. Apply it before running the user-management/authentication backend. Defaults preserve account activation and existing staff UI access. The down migration refuses to remove configured access restrictions until they have been explicitly exported and cleared. See [user management](../docs/USER_MANAGEMENT.md).

The backend uses ordered PostgreSQL SQL migrations in this directory. The existing `users`, `tile_collections`, `enquiry`, sales-bonus tables, shared `products`/`units_of_measure`, shared `customers`, and shared `suppliers` tables are reused; migrations `001`–`010` add billing, store, product, customer, and supplier management structures without recreating those tables.

Configure `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, and `DB_NAME` in the backend environment. Apply migrations with `npm run migrate`. The runner creates `schema_migrations`, applies each pending migration in filename order, and records it in the same transaction. It does not create or drop the database.

Sales draft creation and finalization require the complete billing schema, including migrations 011–018. Invoice prefixes are stored in `store_billing_config`, rather than on `stores`. Migration 021 repairs the stock posting function so it accesses adjustment-only line fields only for stock adjustments; it does not replay or change historical movements. `node --test src/sales.database.test.js` verifies draft creation, dated numbering, payment allocation, stock posting, duplicate finalization, and insufficient stock in a rolled-back transaction.

Before running against production, take a PostgreSQL backup and apply in a staging clone first. Migration 001 has no data migration and does not delete existing rows. Roll back with `npm run migrate:down -- 001_multi_store_foundation.sql` only after exporting any new module data: its down script drops the foundation tables and their contents. For deployments where data must be retained, roll forward with a corrective migration instead of rolling back.

Run application tests with `npm test`. After all pending migrations are applied to a disposable development database, run database integrity checks with `npm run test:db`. These checks use a transaction and roll back fixtures.

Store management adds authenticated endpoints under `/api/tiles/stores`: admins can create/update stores, toggle status, manage assignments, and save billing settings. Any authenticated user can list only their active assigned stores, while Admin can list all. Store details, settings, and invoice sequence configuration are readable only by Admin or an active assignee. Posted sales and purchase invoices snapshot their store identity from the store record.

Migration 006 adds product category, attribute, tax, price, and unit configuration to the pre-existing shared catalog, plus configurable unit conversions. Migration 007 adds a case-insensitive unique SKU index and refuses to proceed if existing SKU values collide; inspect and resolve any reported collision explicitly without deleting records. The APIs are mounted under `/api/tiles/products`; mutations require Admin. No existing storefront gallery records or sales-bonus price configuration are converted into billing products automatically.

Migration 008 extends the existing `customers` table and adds store-attributed customer balance adjustments. Migration 009 links inbound payments to customers for unapplied advances and validates customer-to-invoice allocations. Apply pending migrations with `npm run migrate`. Roll back with `npm run migrate:down -- 009_customer_payment_link.sql` followed by `npm run migrate:down -- 008_customer_management.sql` only after exporting any new customer adjustments or payment attribution; these down migrations drop new customer data and fields. Customer endpoints are mounted under `/api/tiles/customers`; staff financial history is scoped to assigned active stores. `CustomerSearch.jsx` is a reusable customer autocomplete with an add-customer callback; it does not mutate or clear the invoice draft owned by its caller.

Migration 010 extends the existing `suppliers` table, adds store-attributed supplier balance adjustments, and links outbound payments to suppliers for unapplied payments. Roll back with `npm run migrate:down -- 010_supplier_management.sql` before customer migrations if needed; export supplier adjustments and payment attribution first because the down migration drops them. Supplier endpoints are mounted under `/api/tiles/suppliers`. `SupplierSearch.jsx` is a reusable supplier autocomplete with an add-supplier callback; it leaves the purchase draft state with its caller. The repository currently has no purchase invoice creation screen to connect the picker to.

Migration 011 adds `stock_adjustments` and `stock_adjustment_items` and automatically posts stock movements when purchase/sales invoices, sales/purchase returns, stock transfers, or adjustments transition from draft to posted. A posted document transitioning to reversed creates compensating ledger movements in the same transaction. Movement quantities are converted to the shared product base unit using `product_unit_conversions`; missing conversions reject posting. The existing movement trigger remains the only writer to `inventory_balances` and rejects negative resulting quantities. Apply pending migrations with `npm run migrate`. Roll back with `npm run migrate:down -- 011_inventory_management.sql` only after exporting adjustment records; this removes the automatic posting triggers and adjustment tables, but leaves already posted stock movements and balances intact. Restoring the migration later does not replay historical documents, so prefer a corrective forward migration in production.

Inventory APIs are mounted under `/api/tiles/inventory`. Admin can read all stores; Salesperson read access is restricted to active store assignments. Stock adjustments require Admin or an assigned `owner`, `manager`, or `inventory` store role. `GET /` supports store, search, paging, and optional zero-stock rows; `/summary`, `/products/:productId`, `/movements`, `/low-stock`, `/valuation`, and `/reconciliation` provide reports. `POST /adjustments` posts a reasoned adjustment atomically and requires a unique idempotency key. No reservation table currently exists, so reserved quantity is reported as zero and available quantity equals quantity on hand. Valuation uses configured default purchase prices converted to base units; missing prices are reported as unvalued.

Migration 012 extends existing purchase invoice headers and item snapshots and adds explicit `purchase_receipts` and `purchase_receipt_items` for partial shipments. Invoice posting records the supplier liability but does not post stock; each posted goods receipt posts only its received line quantities through `stock_movements`. Receipt totals are serialized against the invoice row, cannot exceed invoice line quantities, and support idempotent retries and reversal. Payment writes reuse `payments` and `payment_allocations`, calculate outstanding balances from posted invoices/returns/allocations, support allocation to multiple invoices, and require an idempotency key. Invoice totals and line taxable/tax/total calculations use PostgreSQL `NUMERIC`. Apply with `npm run migrate`; roll back using `npm run migrate:down -- 012_purchase_management.sql` only after exporting new receipts and payment request keys. Reversal of the migration drops receipt documents but does not remove their ledger movements; use a corrective migration if the data has been used. APIs are under `/api/tiles/purchases`, and require Admin or Salesperson plus access to the invoice's store.

Migration 013 makes sales invoice numbers nullable for drafts, adds finalized product/customer/store snapshots and tax split columns, and validates server-calculated invoice totals on posting. Apply it with `npm run migrate`. The down migration refuses to run while unnumbered drafts remain and drops the new snapshot/calculation fields, so export relevant invoice data before rollback. Sales APIs are mounted at `/api/tiles/sales`: create/update drafts, list and read invoices, finalize, record payments, cancel drafts, and reverse unpaid posted invoices. Finalization locks the invoice, serializes invoice number allocation by store/series/period, checks locked inventory, and posts stock, invoice snapshots, optional initial payment/allocation, and audit event in one PostgreSQL transaction. `SalesBilling.jsx` provides the staff billing and print workflow at `/billing`; finalized invoice snapshots drive print output.

Migration 014 adds customer receipt idempotency, configurable payment method options, reversal actor/reason fields, and immutable posted payment/allocation guards. It reuses `payments` and `payment_allocations`. Apply with `npm run migrate`; rollback is refused after reversal details have been recorded or a payment has used a custom method. Export custom method configurations before rollback. APIs are mounted at `/api/tiles/payments` for receipts, supplier payments, invoice allocation, histories, reversals, daily collections, and custom method setup. Allocation and payment creation run in a transaction, check party/store/status and remaining balances, and preserve original allocations when a payment is reversed. Supplier payment creation remains compatible with the existing purchase endpoint and its `purchase_request_key`.

Migration 015 replaces the prior immediate source-and-destination transfer posting with a dispatched/received workflow. It reuses `stock_transfers` and `stock_transfer_items`, snapshots the unit conversion at dispatch, and adds receipt/discrepancy rows plus the append-only `stock_transfer_transit_movements` ledger for the virtual `IN_TRANSIT` location. Dispatch decrements source stock and increases transit stock in one transaction; receipt adds accepted quantities to the destination and removes accepted, damaged, and shortage quantities from transit. Every dispatched line must be reconciled as accepted, damaged, or short before receipt can post. Existing completed transfer documents are preserved as received. Apply with `npm run migrate`; rollback with `npm run migrate:down -- 015_stock_transfer_management.sql` is refused after managed transfer movements or receipts have been recorded. APIs are under `/api/tiles/transfers`; creation and draft edits require inventory manager access to both stores, dispatch requires source-store inventory manager access, and receipt requires destination-store inventory manager access. Inventory summary and reconciliation include authorized in-transit quantities.

Migration 016 extends the existing sales and purchase return records with return reasons, approval and settlement snapshots, tax adjustments, and request idempotency. It adds per-line sales disposition quantities (`restock`, quarantine, supplier return pending); only the restock quantity enters sellable store inventory. Sales return posting requires a manager approval and checks cumulative returns while locking the original invoice. Purchase returns can only post against quantities received at the store. Posted returns update customer/supplier ledgers from credit amounts without editing original invoices. The APIs are mounted at `/api/tiles/returns`; `GET /` accepts `type=sales|purchase`, `POST /sales` and `/purchase` create drafts, `POST /sales/:id/approve` approves a sales draft, and `POST /:type/:id/post` posts an eligible return. Apply with `npm run migrate`. Roll back with `npm run migrate:down -- 016_sales_and_purchase_returns.sql`; this removes the new workflow fields and is intended only before returns have used those fields. The down migration restores the previous stock trigger, which treated every sales return quantity as sellable stock, so do not roll it back after posting return documents.

Migration 017 adds store/date indexes used by dashboard stock-movement and return reports; it does not alter business data. The dashboard is available at `/dashboard`; its API at `/api/tiles/dashboard` enforces authorized-store scope, uses PostgreSQL aggregation, and paginates filtered reports. CSV export fetches at most 10,000 filtered rows. Gross profit remains unavailable until sales lines preserve a reliable configured cost-method snapshot. Roll back the indexes with `npm run migrate:down -- 017_reporting_indexes.sql` if required.

Migrations 028–032 implement the invoice-style return workflows described in [docs/RETURNS.md](../docs/RETURNS.md). 028 adds versioned return snapshots, original tax components/conversions, immutable invoice credit allocations, actual refund payment links, effective accounting views, and non-sellable return stock. 029 permits retained credit to be applied later with due/party/store guards. 030 reconciles posted return totals/refunds and prevents payment allocations from consuming amounts already covered by return credits. 031 reverses inspection evidence in event order and compensates return-related bonus adjustments. 032 blocks reversal of invoices/receipts supporting active returns or applied credits. Existing invoice/return/payment amounts are preserved; legacy return rows retain workflow version 1. Apply in order with `npm run migrate`. Paired down migrations must be run in reverse order and may refuse once immutable financial or stock evidence exists; prefer forward corrections after business use.

Migration 033 permits a single sales return to reference original item lines from multiple posted invoices for the same customer and store. It reuses existing item foreign keys, header accounting links and JSON snapshots; no amounts or historical records are rewritten. Posting locks and validates all sources, and invoice reversal guards include secondary bills. Apply with `npm run migrate`. The paired down script refuses rollback if multi-invoice return evidence exists. See [multi-bill return workflow](../docs/RETURNS.md#returning-products-from-multiple-sales-bills).

Migration 034 adds store invoice bank/UPI configuration and immutable payment snapshots for sales invoices. Existing terms fields and posting snapshots are reused. Apply with `npm run migrate`; existing stores start with empty payment details and historical invoices are unchanged. The paired down script refuses rollback if invoices contain saved payment instructions. See [sales invoice terms and payment instructions](../docs/INVOICE_SETTINGS.md#sales-invoice-terms-and-payment-instructions).

Migration 035 adds optional salesperson/tile-mistiri referral links and name snapshots to sales invoices. Apply with `npm run migrate`; existing invoices remain unassigned. New and edited drafts validate that a selected referral is an active eligible user.

Migration 036 enables invoice-driven sales bonuses. Posted invoices now create bonus records for the selected referral only; existing cost, product bonus-rate, eligibility, and salesperson-versus-tile-mistiri calculation rules remain in effect. Invoice referrals are sourced directly from `sales_invoices`; staff no longer need a separate recipient assignment for the invoice.

Migration 037 adds invoice-bonus approval snapshots and an append-only bonus-payment history with idempotency keys. Invoice-linked records are pending approval until Admin approval; approved payable amounts accrue with posted customer collections. Returns and invoice reversals continue to append bonus adjustments, and already-paid amounts remain visible as recovery due. The down migration refuses to remove payment history after it has been used.

Migration 038 records an Admin payout override when an approved invoice bonus is paid before customer collections make the full bonus payable. Admins may record a partial or full payout up to the approved bonus less return/reversal adjustments; normal payable amounts still accrue with collections unless Admin explicitly pays early. Early payout is retained across later collection refreshes.

Migration 039 records risky bonus approvals made while the related sales invoice has an outstanding balance. The approver must provide a reason; the unpaid invoice amount at approval and reason are retained with the approval record.
